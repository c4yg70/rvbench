## 1. 批量作业

### 1.1 动机（实测依据）

K3 实测单作业拆解：`import flag_gems` **11.61 s** + `import torch` 4.47 s + triton 编译（冷 60~90 s）+ 执行。
单作业端到端 84.5 s（T4 n=10）。**候选代码导入的固定成本与 shape 数无关** → N 个 shape 批量跑，只付一次。

粗算 N=5：5×84.5=422 s → 约 16 s（一次 import）+ 编译 + 5×执行 ≈ 100 s，**~4×**。

> 注意：`import flag_gems` 11.61 s 是**热 page cache 稳态值**（探针 n=3 取 min），说明它是模块级代码执行的 CPU 成本，**不是 IO**。

### 1.2 契约

```json
POST /jobs
{
  "bench": "op", "warmup": 5, "rep": 5, "timeout_min": 15,
  "cases": [
    {"op": "add", "shape": "64,512,512", "dtype": "float32"},
    {"op": "add", "shape": "1024,1024",  "dtype": "float32"},
    {"op": "add", "shape": "8,4096",     "dtype": "float16"}
  ],
  "files": [{"path": "flag_gems/ops/add.py", "content": "..."}]
}
```

**向后兼容**：无 `cases` 字段 → 由顶层 `op/shape/dtype[/batch]` 构造单 case，行为与现在**逐字节一致**。

### 1.3 校验（在 `validate_request` 内）

| 规则 | 错误码 |
|---|---|
| `cases` 必须是 list，长度 1..`batch_cases_max`（新配置，默认 16） | 400 |
| 每 case 的 `op`/`shape`/`dtype` 走现有同一套 `RE_OP`/`RE_SHAPE`/`OP_DTYPES` | 400 |
| gemm：每 case `op ∈ GEMM_OPS`，可带 `batch` | 400 |
| **禁止** case 级覆写 `warmup`/`rep`（口径必须统一，acc/func 强制 0/1 才好做） | 400 |
| `files` 上限仍 32，**对整个批量作业只部署一次** | 400 |
| `timeout_min` 是**整个批量作业的墙钟预算** → 必须 ≥ `len(cases) × min_case_timeout_min`（新配置，默认 0.5），否则必然超时丢全部结果 | 400 |

### 1.4 执行

- **一次 deploy → 一次 executor 调用 → 子进程内循环 N 个 case → N 行 JSON**
- warmd `_run_bench`：在 fork 出的子进程里 `for case in cases:` 调 bench 并 print 一行 JSON（**不要求 bench 脚本改参数**，最小侵入）；`import flag_gems` 只付一次
- warmd `_parse_json_limits` 的 `cap=16` → 改为随 `batch_cases_max`
- 每行输出必须带 `case_index`（0..N-1），供 evald 对齐回 case

### 1.5 结果契约（**关键设计决策**）

```json
"result": {
  "n_cases": 3, "n_ok": 2, "n_failed": 1,
  "cases": [
    {"case_index":0, "op":"add","shape":"64,512,512","dtype":"float32",
     "ok":true, "torch_ms":..,"gems_ms":..,"speedup":..,"correct":..,
     "max_abs_err":..,"metric":"speedup","psr":8},
    {"case_index":1, ..., "ok":true, ...},
    {"case_index":2, ..., "ok":false, "error":"..."}
  ]
}
```

**决策：提交了 `cases` 的作业，`result` 顶层不再放 `speedup`/`torch_ms` 等标量，只有 `cases[]`。**

理由（两条，都踩过事故）：
1. 若顶层放 case[0] 的标量，老驱动会**静默只看第一个 shape** → 静默错判。项目已有事故史（越权写者导致 6 份错判）
2. 若顶层放聚合值（中位数/几何平均），等于**凭空造出一个新的论文数字口径**，比报错更危险

→ 顶层没有 speedup，老驱动读到 `None` 会**显式失败**，风险可控。
→ **`bin/eval_pipeline.py` 必须同步支持读 `result.cases`**，这是批量落地的前置条件。

**终态语义（不新增状态枚举）**：
- 子进程 rc=0 且 ≥1 个 case 成功 → `done`；全失败 → `failed`
- 每 case 的成败在 `cases[i].ok` / `cases[i].error`
- func 车道：`kope_mem.pass_rate = n_ok / n_cases`（自然扩展"跑通即 pass"）
- timing 车道：每 case 各带自己的 `psr`（PSR≥8 验收字段，逐个判）

### 1.6 风险

| 风险 | 缓解 |
|---|---|
| 单作业墙钟变长，超时丢全部结果 | `timeout_min` 下界硬校验（§1.3） |
| 不同 shape 可能触发多份 triton 编译（未实测） | 先在小 N（3~5）试点，用 §4 新指标 `evald_job_duration_seconds` 观测 |
| 下游驱动必须升级 | 列为批次前置条件，不改驱动不发布 |
| 队头阻塞（长作业卡住短作业） | **配套 §3 优先级**；批量作业默认 `priority=0` |

## 2. flag_gems import 调优

### 2.1 已知事实（K3 实测）

| 项 | 值 |
|---|---|
| `import torch` | 4.47 s |
| `import flag_gems` | **11.61 s**（热 page cache，n=3 取 min） |
| `bash source run_env + python -c pass` | 0.04 s |
| CPython 启动 | 32.6 ms |

**修正上一版报告**：我原建议"warmd 父进程预热 page cache"，实测 11.61 s 已是热态值 → **预热收益≈0，排除**。11.6 s 是执行 237 个算子模块级代码的 CPU 成本。

### 2.2 四条路径

| 路径 | 做法 | 预期 | 风险 | 判断 |
|---|---|---|---|---|
| **A. 批量化摊薄**（§1） | 一次 import 跑 N case | **确定有效** | 低 | **推荐** |
| B. 惰性导入 | `flag_gems/__init__.py` 改 `__getattr__` 懒加载 | 若只加载 1 个 op，可能降到 1-3 s | **高**：FlagGems registry 可能依赖 eager import；改的是第三方库 | 实验 |
| C. 只 import 子模块 | bench 侧 `import flag_gems.ops.<op>` | **大概率无效**——import 子模块会先执行父包 `__init__` | 低 | 先测再定 |
| D. 绕过包 `__init__` | `sys.path` 直插 ops 目录裸 import | 破坏包语义 | 极高 | 不做 |

### 2.3 建议

**§1 批量化是唯一确定有效且低风险的路径。B 降级为"有时间再做的实验"**——动第三方库的风险与当前论文周期不匹配。

若要开 B，先做 2 项低成本测量（**本次未执行**，用户要求先不上板）：

```bash
python -X importtime -c "import flag_gems"        # top N 模块 self 耗时
python -c "import flag_gems.ops.add"              # 验证 C 路径是否仍付全量
```

判定线：若 `__init__` 净成本 < 3 s，B 无意义，彻底放弃。

## 3. 提交优先级

### 3.1 契约

| 项 | 值 |
|---|---|
| 字段 | `"priority": <int>` |
| 取值 | **0..9，默认 0，越大越优先** |
| 校验 | 非 int 或越界 → 400（与现有校验风格一致） |
| 回显 | body 无 `priority` → `sanitized` **不带** priority 键（与 `lane` 同款向后兼容约定，老客户端落盘逐字节不变） |
| 作用范围 | **仅同车道内**排序；车道间资源独立，不跨车道 |
| **抢占** | **不抢占正在运行的作业**（运行中持锁且已部署文件，强杀会留脏状态）—— 与 `cancel()` 只处理 queued 一致 |

### 3.2 队列改造

现状：`self.queues[lane] = deque()`，FIFO，`next_job` 用 `popleft()`。

改为 **10 个优先级桶**（不用 heapq）：

```python
self.queues[lane] = {p: deque() for p in range(0, 10)}
```

- `submit` → 入 `queues[lane][prio]`
- `next_job` → 从 prio=9 扫到 0，取第一个非空桶的队头（O(10)）
- `position` → 本桶内 index+1（**语义变化**：不再是全局执行序，文档须写明）
- `cancel` → 从对应桶 remove（O(桶长)）

选桶而非 heapq 的理由：`cancel`/`position` 从 O(n) 降到 O(桶长)，实现简单可预测。

### 3.3 饥饿防护（aging）

- 新配置 `priority_aging_s`（默认 600，0=关闭）
- `next_job` 时**惰性**升级：等待超阈值的作业 priority+1（封顶 9）并搬桶，无需后台线程
- 老客户端全在 0 桶 → 行为与现在一致

### 3.4 配置与交互

```json
"priority_max": 9,
"priority_aging_s": 600
```

- 队列满（> `queue_max`）→ 一律 429，**不做高优抢占**（丢作业比排队危险）
- 批量作业默认 `priority=0`；调用方可显式下调（未来若引入负值语义另议）

### 3.5 metrics

`evald_queued{lane,priority}`（3 车道 × 10 桶 = 30 序列，基数可接受）

### 3.6 空闲准入闸门（idle gate）—— baseline 重跑场景

**需求**：服务器空闲时重跑 baseline，baseline 优先级低于正常任务。

#### 3.6.1 定性：这是准入控制，不是排序

「空闲时才跑」**不能靠 priority 表达**。理由（代码事实）：

- `self.queues[lane]` 每车道一个 deque + 单 worker 串行 → **队列空 ≠ 服务器空闲**
- 8 个子代理的提交是突发式的：队列刚空 0.5 s 就把 baseline 派发，它立刻
  `flock(/tmp/k3_bench.lock)` 占住 timing 车道整段时长
- **baseline 与正常作业同粒度**（都是单点算子，84 s 量级）：单次队头阻塞的代价与正常作业相同，
  看起来无害——但 **237 个 baseline ≈ 5.6 h 的车道时间是纯增量**

时间线（baseline 84 s、去抖 30 s、正常作业在 t=50 到达）：

| 方案 | 结果 |
|---|---|
| 纯优先级（队列一空就派发） | baseline t=40 起跑至 t=124，正常作业 **阻塞 74 s** |
| 空闲闸门（去抖 30 s） | 正常作业 t=50 打断倒计时并先跑，baseline 让行至 t=120 |

**闸门的价值不是"减少单次阻塞时长"（两者同为 84 s），而是把 5.6 h 车道占用从「争抢」变成「填空」**：

| | 无闸门（只靠 priority） | 有闸门 |
|---|---|---|
| 237 个 baseline 的车道占用 | 5.6 h，全部计入正常作业的排队延迟 | 5.6 h，落在原本无人使用的时间 |
| 正常作业延迟分布 | 整体右移 | 基本不变 |
| 最坏单次阻塞 | 84 s | 84 s（相同——闸门只管准入，管不了已启动的作业） |
| baseline 能否在白天板空时跑 | 不能（要等 cron 窗口） | 能 |

#### 3.6.2 契约

提交字段 `idle_only: bool`（默认 false）。**独立于 `priority`**：

- `idle_only=false` → 现有行为，按 priority 桶调度
- `idle_only=true` → 只有满足空闲判据才准入；**准入后不再特殊对待**（不抢占、不降 cpu）
- baseline 之间仍用 `priority` 排序（baseline 内部也有轻重缓急）

向后兼容：body 不带 `idle_only` 则 sanitized 不带该键（与 `lane` / `priority` 同款约定）。

#### 3.6.3 判据与配置

```json
"idle_only_enabled": true,
"idle_gate_delay_s": 30,
"idle_gate_scope": "lane",
"idle_only_max_wait_s": 14400
```

```python
def lane_idle(lane):
    # 同车道无运行中作业 且 无（非 idle_only）排队作业
    return running_count[lane] == 0 and len(queues[lane]) == 0
```

- `idle_gate_delay_s`：去抖窗口。车道由忙转空时记 `idle_since`，期间任何普通作业到达即重置
  → 吸收突发提交间隙
- `idle_gate_scope`：`lane`（默认，只看同车道）/ `global`（所有车道全空）。
  acc/func 不持 bench 锁，默认 `lane` 允许 baseline 与 func 并行；CPU 争用时改 `global`
- `idle_only_max_wait_s`：等待超阈值（默认 4 h）→ 降级为普通作业强制准入，防饿死/活锁

#### 3.6.4 调度器改造（`_scheduler_loop`）

```
cand = pick_normal_job(lane)          # 10 个 priority 桶
if cand: dispatch(cand); continue
if not lane_idle(lane): idle_since[lane] = None; continue
if idle_since[lane] is None: idle_since[lane] = now
if now - idle_since[lane] >= idle_gate_delay_s:
    b = pick_idle_only_job(lane)
    if b: dispatch(b)
```

被闸门拦住的作业 `state` 仍为 `queued`，额外回显 `idle_gated: true`（**不新增 state 枚举**）。

#### 3.6.5 备选方案与否决理由

| 方案 | 判断 |
|---|---|
| 独立 `lane=baseline` | **否决**。baseline 是 timing 语义、要持同一把 bench 锁；新车道 = 复制锁/资源逻辑，且破坏"仅 timing 持锁"的 ADR-0002 不变式 |
| SIGSTOP 暂停 / 抢占 | **否决**。被挂起的进程仍持有 flock 不推进（= 死锁风险），且 torch 显存不释放会让后续作业 OOM |
| WFQ 权重 / 时间片 | **否决**。单车道串行下退化为准入控制，纯过度设计 |
| cron 夜间时间窗 | **保留为兜底**，与 `idle_only_max_wait_s` 二选一解决饿死；不能当主方案（白天板空了也跑不了） |
| **外部轮询协调器**（客户端看 /metrics 自己决定提交） | **单点 baseline 场景下首选**——见 §3.6.6。**evald 零改动**；粒度天然 84 s，最坏只阻塞 84 s；baseline 只有一个提交方，无多客户端雪崩。**批量化落地后失效**（届时再上服务端闸门） |
| `priority: -1` 表达"最低优先级" | **否决**。§3.3 的 aging 会把 −1 升到 0，负值语义与老化机制直接冲突；且负数表达不了"空闲才跑"的准入含义。用独立 bool `idle_only` |
| **结果去重 / 缓存** | **强烈推荐配套**。命中已有有效 baseline 就别跑——最好的调度是不调度。见 §3.6.7 |

#### 3.6.6 推荐路径：先外部协调器，服务端闸门留到批量化之后

**baseline 是单点算子（与正常作业同粒度 84 s）这一事实，让「不改 evald」成为当前最优解。**

**阶段 1（现在就做，evald 零改动）** —— 外部协调器 `bin/baseline_runner.py`：

```
loop:
  m = GET /metrics
  if m.queued{lane=timing} == 0 and m.running{lane=timing} == 0
     and 该状态已持续 >= idle_observe_s(默认 300):   # 观察窗口，比服务端去抖更长
       提交 1 个 baseline 作业（单点算子）
       long-poll 等它完成                            # 天然节流：一次只占 84 s
  else:
       sleep(30)
```

- 一次只提交 1 个 → **最坏只阻塞 84 s，与一个正常作业等价，不会比现状更差**
- 有限工作量（237 个）+ 单一提交方 → 不存在多客户端同时看到空闲的雪崩
- 已完成算子写 manifest → 崩溃可断点续跑
- 只依赖一个新指标 `evald_running`（§4 已规划），其余用现有 `evald_queued`

**残余风险**：提交后 84 s 内到达正常作业仍会被阻塞（闸门在客户端，无法撤回）。
用更长的 `idle_observe_s` 压低概率，代价是 baseline 吞吐下降。

**阶段 2（§1 批量化落地之后）** —— 服务端 `idle_only` 闸门（§3.6.2–3.6.4）：

- 批量化后单作业时长翻 N 倍，"最坏 84 s"的上界不再成立 → 必须服务端把关
- 届时 `idle_only` 作业需服务端 `timeout_min` 硬顶（建议 ≤ 5 min）并重设 `idle_gate_delay_s`
- **若批量化未落地，服务端闸门没必要做**——阶段 1 已覆盖需求

#### 3.6.7 配套：baseline 结果去重（削减总量，优于调度优化）

237 算子 × 84.5 s ≈ 5.6 h 量级（按现有单作业口径粗估，不含排队）。重跑前先查：

同一 `(op, shape, dtype, flag_gems_commit, torch_version)` 已有 `state=done` 结果且未过期 → 跳过。

- 落点：优先放在**提交侧脚本**（evald 不改动、零风险）；若要做成服务端门禁，
  需引入 `dedupe_key` + manifest 校验，**属独立议题，不在本批次**
- 风险：代码版本变了但 key 未变 → 静默复用陈旧 baseline → 污染论文数据。
  提交侧实现时必须把 `flag_gems` git commit 计入 key

#### 3.6.8 metrics

```
evald_idle_gated_jobs{lane}                        gauge    当前被闸门拦住的作业数
evald_idle_gate_blocked_total{lane,reason}         counter  reason: lane_busy | debounce
evald_idle_only_oldest_wait_seconds{lane}          gauge    最老 idle_only 作业等待时长（配 max_wait 用）
```

`evald_job_duration_seconds` / `evald_queue_wait_seconds` 增加 label `idle_only="true|false"`
——**仅 2 个取值，不触发基数爆炸**（对比：禁止把 `op` 放进 label，237 算子）。

#### 3.6.9 selftest 与风险

- 新增 selftest 用例：**用临时 config 注入 `idle_gate_delay_s: 0.5`**，不要真等 30 s
  1. 有普通作业排队时提交 `idle_only` → 断言不被派发
  2. 车道空闲满 0.5 s → 断言被派发
  3. 去抖期间提交普通作业 → 断言 idle_only 让行、倒计时重置
- 风险 1 **活锁**：持续有普通作业 → baseline 永远跑不到。靠 `idle_only_max_wait_s` 或夜间窗口兜底
- 风险 2 **与 `force_lane` 的交互**：K1 池锁死车道时 `idle_only` 仍在最终车道内生效，无冲突
- 风险 3 **QEMU 假绿**：flock/进程语义在 QEMU 下不可信，**必须真板复验**

## 4. /metrics 遥测信号

### 4.1 现状与缺口

现有 8 指标（`up`/`queued{lane}`/`running{lane}`/`submissions_total`/`jobs_total{state}`/`last_submission_ts`/`last_completion_ts`/`last_job_info`），与 textfile 探针逐字一致（见 `results/k1/evald/METRICS.md`）。

**完全看不到的东西**：

1. 排队多久（只有瞬时 queued 数，没有时长）→ 无法判断争用
2. 作业跑多久 → **没有任何时长信号**
3. 吞吐 → 只有总计数，没有按 lane/state 的完成计数（rate 不友好）
4. 队列是否老化（最老作业等了多久）
5. warmd 故障回退 subprocess → **隐形故障，零信号**
6. restore 失败 → **P0 级**（`实验环境.md` §4.6：restore failed 要 HALT），零信号
7. 优先级分布（§3 新增后必需）

### 4.2 新增指标

| 指标 | 类型 | labels | 说明 |
|---|---|---|---|
| `evald_queue_wait_seconds` | histogram | lane | 排队时长 |
| `evald_job_duration_seconds` | histogram | lane | 执行时长（贴合 84.5 s 均值） |
| `evald_jobs_completed_total` | counter | lane, state | 终态计数，`rate()` 用 |
| `evald_oldest_queued_age_seconds` | gauge | lane | 队列最老作业等待时长，告警用 |
| `evald_executor_fallback_total` | counter | reason | warmd→subprocess 回退次数 |
| `evald_restore_failures_total` | counter | — | 恢复失败（P0） |
| `evald_spool_jobs_total` | gauge | — | jobs/ 目录数（当前 898 且永不清理） |
| `evald_queued` 扩展 | gauge | lane, **priority** | §3 配套 |
| `evald_batch_cases_total` | counter | lane | §1 批量 case 数 |
| `evald_http_requests_total` | counter | path, code | HTTP 层 |
| `evald_longpoll_active` | gauge | — | 长轮询挂起数 |
| `evald_psr` | histogram | lane | 作业验收字段（PSR<8 = infra 失败） |

### 4.3 设计原则（写进代码注释）

1. **零依赖**：stdlib 手写文本渲染，ADR-0003 不变
2. **持久化分两类**：
   - `submissions_total` / `jobs_total`：继续 spool 扫描衔接，**重启不回落**
   - **histogram 与瞬时 gauge：进程内语义，重启清零**——无法从 spool 便宜重建（898+ 目录且增长）。**必须在 `# HELP` 文本里写明**，否则会被误读为 counter reset
3. **渲染必须 O(1)**：不得扫 spool。`evald_spool_jobs_total` 用运行期计数器维护，不是扫描
4. **名字不得与 textfile 探针冲突**：已核对 `evald-probe.sh` 的 9 个名字（`evald_up/queued/running/submissions_total/jobs_total/last_submission_timestamp_seconds/last_completion_timestamp_seconds/last_job_info/probe_success`），新增名无冲突
5. **基数控制**：histogram label 只用 lane（3 值）。**禁止把 op 放进 histogram label**（237 算子 × bucket = 序列爆炸）；`last_job_info` 维持只输出一条

### 4.4 固定 bucket（写死，不做动态）

- `queue_wait_seconds`: 1, 5, 15, 30, 60, 120, 300, 600, +Inf
- `job_duration_seconds`: 5, 15, 30, 60, 90, 120, 300, 600, +Inf
- `psr`: 1, 2, 4, 8, 16（PSR≥8 为验收线）

### 4.5 埋点位置

| 位置 | 埋点 |
|---|---|
| `Store.submit()` | 复用 `submitted_at` 作排队起点 |
| `Worker.run_job()` 设 `started_at` 处 | `queue_wait += started - submitted` |
| `Store.finish()` | `duration += finished - started`；`m_completed[lane][state] += 1`；spool 计数 +1 |
| `WarmForkExecutor.run()` 的 except 分支 | `m_fallback[reason] += 1` |
| `Worker.run_job()` 的 restore except | `m_restore_fail += 1` |
| `Handler.do_GET/POST/DELETE` | `m_http[path][code] += 1` |
| `Handler._get_job()` 长轮询进出 | `m_longpoll ± 1` |

### 4.6 验收

selftest 新增 `[15] /metrics 遥测信号` 节：
- 文本含全部新指标名与 `# TYPE` 行
- 注入一次 restore 失败 → `evald_restore_failures_total` +1
- 注入一次 warmd 故障 → `evald_executor_fallback_total` +1
- histogram bucket 单调递增、`_sum ≤ _count × max_bucket`
- 与 textfile 探针并行对账（沿用 `METRICS.md` §3.8 流程）

### 5.2 价值

1. **统一 uuid7 语义**：K3 系统 3.14.4（原生）/ K1 3.12.3（fallback）→ 统一后 `/jobs?since=` 的 UUIDv7 时间序游标两侧一致

### 5.3 落地命令（可复制）

```bash
# 1) 系统级装 uv（root，一次性）

# 2) 以 c4y 身份装 3.14 到栈内目录（关键：必须用 su - c4y，见 §5.4 坑 1）

# → /home/c4y/autoke/.uv-python/cpython-3.14-linux-riscv64gc-gnu/bin/python3.14

# 3) 自检（不监听端口；服务运行中可跑；必须以 c4y 身份，见 §5.4 坑 2）
su - c4y -c 'cd /home/c4y/autoke/evald && \
  /home/c4y/autoke/.uv-python/cpython-3.14-linux-riscv64gc-gnu/bin/python3.14 \
  evald.py --selftest --config config.json'

# 4) 切换：改 evaldctl.sh 的 PY 变量 → stop → start
```

### 5.4 坑（本次实测踩到，必记）

1. **`sudo -u c4y` 不重置 HOME** → uv 去读 `/root/uv.toml` → `Permission denied`。
   **必须用 `su - c4y -c '...'`**（login shell 正确设 `HOME=/home/c4y`）
2. **以 root 跑 selftest 会污染 `/tmp/k1_bench.lock` 的属主** → root 创建后，c4y 的 evald 在
   `os.open(lock_file)` 报 `PermissionError`，**timing 车道直接失效**。
   本次实测踩到（`ls -l` 显示属主变成 root），已 `chown c4y:c4y` 修复并复验通过。
   **纪律：板上一切 evald 相关命令（含 selftest）一律以 c4y 身份执行**
3. uv 默认把 python 装到 `~/.local/share/uv/python`，多板复制不便 → 显式设 `UV_PYTHON_INSTALL_DIR` 到栈内
4. 当前 230 上 root 与 c4y 各有一份 3.14（`/root/.local/share/uv/...` 与 `/home/c4y/autoke/.uv-python/...`）——**root 那份应删除**避免混淆

### 5.5 建议节奏

- **不立刻切生产**：evald 在 3.12.3 与 3.14.7 下 selftest **均全绿** → 切换无功能收益，唯一收益是 uuid7 一致性
- 先在 230 debug 板切 3.14 观察几天 → 无差异再推 233/241/243
- **K3 系统已是 3.14.4，不需要 uv 装 3.14**（除非要锁版本防系统升级）

## 7. 实现记录（2026-09-09 下午：最近 3 作业指标 + batch shape 修正 + K3 收口）

handoff（`handoff-evald-batch-metrics-20260909.md`）之后的落地。代码正本 = 仓库 `evald.py`（md5 `aeed0769…`，2137 行）。

### 7.1 最近 3 作业指标（k1-monitor README §5 需求）

新增 3 个 gauge（label `idx`(0/1/2)/`op`/`state`）：`evald_recent_job_duration_seconds`、
`evald_recent_job_queue_wait_seconds`、`evald_recent_job_finished_timestamp_seconds`（**epoch 秒**）。

- 数据结构：`Store.m_recent = deque(maxlen=3)`，元素 `(op, state, dur, wait, fin_epoch)`。
- live 路径：`finish()` 里 `appendleft`，O(1)，deque 自动淘汰最旧。
- **重建路径**：`_init_metrics` 扫 spool 时顺带收集 `state∈{done,failed,timeout}` 且 `duration_s` 非空的作业，
  按与 `last_job_info` **相同的排序键** `(result.json mtime, ISO finished_at)` 倒序取前 3。
  → 与 `submissions_total`/`last_job_info` 同源语义（spool 权威、重启无缝），**非**进程内 histogram 的清零语义；
  重启后无需等新作业即点亮（K3 实测从 978 作业 spool 重建出 less_equal/less/leaky_relu 三条真实历史）。
- 基数：瞬时 gauge 最多 3 条序列/指标；`op` 进 label 是面板必需（K3 大卡显示算子名），随作业 churn 的序列总量
  受「近期出现过的算子数」约束（≪ per-op histogram 的 237×bucket×lane）。`board` 由 Prometheus relabel 注入。
- selftest 新增 `[17]`：ring buffer 只留 3、idx0=最新倒序、三指标存在、idx/op/state 三标签、
  finished_timestamp>1e9（epoch）、**重启从 spool 重建顺序一致**。

### 7.2 per-op histogram（README §5「顺带建议」）——未采纳

`evald_job_duration_seconds` 已是 per-lane histogram（`histogram_quantile` + 按车道均值可用）。
加 `op` 标签违反 §4.3 基数红线（237×8bucket×3lane 且 histogram 序列永不淘汰）。按 op 的长期回归走 spool 离线口径。

### 7.3 batch `cases[i].shape` 修正

真实 `bench_op.py` 把 shape 输出成 list（`[64,512,512]`），而结果契约（§1.5）与驱动按提交字符串对齐。
`_map_rows` 多 shape 分支改为**一律用提交的 `shapes[i]`（字符串）覆盖** `cases[i].shape`（单 shape 路径不变，保持逐字节兼容）。
selftest `[16]` 加固：合成 bench 行改用 list 形态 shape，真正捕获此类漂移（原用 string 形态掩盖了它）。
230 与 K3 的 B-batch E2E 均已从「shape 是 list」转绿为「shape 是提交字符串」。

### 7.4 selftest `[9]` 对 acc-停用配置的健壮性

旧 `[9]` 硬编码 `s1["warmup"]`（s1=correctness 车道请求）；在 `correctness_workers=0`（acc 停用，如 K3 计时板）时
`validate_request` 正确返回 `s1=None` → `TypeError` 崩溃，并连带复用 s1 的 `[10]-[15]` 全崩。
改为用**强制启用 acc 的 `cfg_acc` 变体**产出 s1（与生产开关解耦），并新增「acc 停用时 correctness 车道被拒」断言。

> K3 生产 config（acc 停用 + `correctness_cpus=12-14` 属 A100）下，selftest `[11]/[12]/[14]` 仍会 FAIL：
> correctness worker `taskset -c 12-14` 需 A100 注册（selftest 进程未注册、默认 X100 亲和）→ EINVAL；`[14]` 缺省推导断言期望 acc 开。
> 这些是**环境性既有 FAIL**（METRICS §3.4 同类），非补丁缺陷——补丁门禁以 230（acc 启用、同 md5）**ALL PASS** 为准，
> K3 以**运行时真计时作业**（A100、affinity 8-15、E2E done）为准。
