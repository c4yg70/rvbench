## 1. 问题陈述

### 1.1 现状链路

```
现宿主（riscv64，10.18.60.100）                    开发机
├─ node_exporter :9100（~/ne，@reboot 兜底）      Docker 容器 k1-prom（Prometheus :9090，绑 127.0.0.1）
├─ evald :8788 /metrics（A100 簇 cpu8-15 计时）──30s 拉取──▶  job=boards / job=evald
└─ evald :8791 /metrics（X100 簇 cpu0-7 acc+func）           └──▶ dashboard.html（file:// 直开，前端算告警）
```

数据方向只有一条：**开发机 → 宿主**。枢纽（Prometheus 容器）与面板宿主都在开发机上。

### 1.2 痛点

| # | 痛点 | 后果 |
|---|---|---|
| 1 | 告警全部由 `dashboard.html` **前端计算** | 浏览器不开＝无告警；无通知渠道、无恢复通知、无屏蔽窗口、无告警历史 |
| 2 | Prometheus 无长期保留（缺省 15d） | 温度劣化、队列积压周期一类历史趋势无数据可查 |
| 3 | 面板是手工单文件，图表不可组合、无变量、无权限 | 只有一人一屏一种视图 |
| 4 | 宿主侧只有 node_exporter 单指标面 | 业务与主机指标无统一采集器框架，扩展靠改抓取配置 |
| 5 | 告警阈值散落在 `dashboard.html` JS 里 | 阈值即代码；改阈值须动冻结物（要过宿主上 selftest 门禁） |
| 6 | 枢纽寄居开发机（容器 ＋ 宿主网络假设） | 观测链路可用性挂在开发机开机与容器存活上；且宿主 → 枢纽方向从未打通 |

### 1.3 新事实：第二块 K3 板（本 spec 的前提变更）

第二块 K3 板即将到位，拓扑据此按**宿主级分工**重构：

- 一块板专责 **perf 计时测试**（下称**计时节点**，即 evald :8788 所在宿主）；
- 另一块承担 **acc、func 与 Nightingale 这类监控、面板组件**（下称 **枢纽节点**，同宿主承载 acc/func 实例 :8791）。

因此计时隔离从「核簇隔离」升级为**宿主级隔离**：监控枢纽不再与计时簇同宿主，观测链路也不再依赖
开发机、容器宿主或端口转发一类的宿主耦合。**物理哪台宿主承担哪个角色由板清单声明**（§2.1），
spec 不写死宿主数量与身份。

### 1.4 目标

- **记录**：VictoriaMetrics 单机版承接全部时序（retention 90d），API 与 Prometheus 同构。
- **采集**：Categraf 统一宿主侧采集——主机指标（`input.node_exporter`，`node_*` 命名 100% 兼容）
  ＋ 业务指标（`input.prometheus` 抓 evald 实例，evald 零改动）。
- **可视化与告警**：Nightingale 单二进制（内置 SQLite，零外部 MySQL/Redis）承担大盘（四层重建）
  ＋ 告警引擎（9 族规则、通知媒介、屏蔽天窗）＋ 用户/业务组。
- **拓扑**：枢纽落宿主侧（枢纽节点本体），无容器宿主依赖、无端口转发。
- **不变量**：七件冻结物零改动；`node_*`/`evald_*` 序列名与 `job`/`board`/`role`/`cores`/`clusters`/
  `workers` 标签语义保持原义，既有 PromQL 查询资产（面板与告警）原样复用。

### 1.5 现状盘点（2026-09-20 调研结论，沿用）

1. **指标面**：evald 原生 `/metrics`（exposition 0.0.4，免 token）产出 `evald_up`、
   `evald_queued{lane}`、`evald_running{lane}`、`evald_jobs_total`、
   `evald_jobs_completed_total{lane,state}` 等；主机侧 node_exporter 产出 `node_cpu_seconds_total`、
   `node_memory_*`、`node_filesystem_*`、`node_hwmon_fan_rpm·pwm·fault`、`node_hwmon_temp_celsius`、
   `node_uname_info`、`node_network_*`、`node_network_address_info`。
2. **面板依赖**（`dashboard.html` 反查）：只调 `GET /api/v1/query` 与 `/api/v1/query_range`
   （:921 单处 fetch 封装）→ VM API 同构即理论零改动可切数据源；选择器锚定 `{job="boards"}` /
   `{job="evald"}` 并有 `{job!="evald"}` 回退分支；**核簇堆叠柱与 worker↔核命名读 `up{job="boards"}`
   的 `clusters` / `workers` 静态标签，且取「末条命中」**（:1281-1293，逐条覆盖式读取）；板卡注册表
   以 `board` 标签为键（:1240-1301，`job="boards"` 出主机卡、`job="evald"` 出作业卡，两源独立增删）。
   默认数据源 `DEFAULT_PROM = "http://127.0.0.1:9090"`，可用 `?prom=<url>` 覆盖并记忆于 localStorage。
3. **告警口径**（monitor/README「面板结构」§2，9 族）：主机失联、evald 实例离线、温度 ≥70/85、
   簇均核占用 ≥80/92、swap ≥60/80、内存/硬盘 ≥80/92、风扇 fault、队列 ≥20/50。
4. **冻结物**（零改动承诺）：见文首七件；工作副本＝宿主侧字节，md5 基线见 CHANGELOG。
5. **网络现状**：开发机 → 宿主方向（拉取 :9100/:8788/:8791、SSH）通；**方向反转（宿主 → 枢纽推送）
   从未使用**，且新拓扑下变成**宿主 → 宿主**，P0 必须先验证。
6. **外部组件事实**（2026-09-20 调研；标注「未核实」者本轮未做外部核实，列为 P0 门禁）：
   - **Nightingale**：v9.1.1（2026-08-18）为最新；官方发布物为 **linux amd64/arm64 tarball**
     （无 Windows 原生包），二进制部署解压即启（`:17000`，缺省账号 root/root.2020）；
     **单机轻量模式内置 SQLite ＋ miniredis**，免外部 MySQL/Redis；生产模式改 etc 配置
     `[DB]/[Redis]` 外接（HA＝多实例共用一套外部存储）。官方将轻量模式定位为测试/体验
     （单宿主单用户场景接受该取舍，见 R6/R7）。**riscv64 发布物是否存在未核实** → R1。
   - **VictoriaMetrics 单机版**：默认 `:8428`；`-promscrape.config` 可直接吃 Prometheus 语义配置；
     `/api/v1/query(_range)` 与 remote write `/api/v1/write` 兼容；`-retentionPeriod` 缺省 31d。
     **riscv64 发布物是否存在未核实** → R1。
   - **Categraf** v0.5.18：`conf/config.toml` 有 `[[writers]]`（remote write，支持 basic_auth）、
     `[heartbeat]`（10s 报 n9e `/v1/n9e/heartbeat`）、`[global.labels]`；`input.node_exporter`
     内嵌官方 node_exporter 核心逻辑、`node_*` 指标 100% 兼容（与原生 cpu/mem 套件二选一）；
     `input.prometheus` 对目标 `/metrics` 指标与标签 100% 保真透传，默认以 URL 作 `instance` 标签
     （**实例级 labels 未见于 README** → R4）。**无官方 riscv64 发布物**（amd64/arm64/windows）。
   - Nightingale v6 起不再生成 `target_up` 指标，机器失联以**心跳超时**（Targets 在线态）判定。

## 2. 方案概述

### 2.1 角色化宿主分工（板清单声明）

| 角色 | 职责 | 采集器 | 枢纽组件 | 钉核约束 |
|---|---|---|---|---|
| **计时节点**（计时正本） | evald `:8788`（A100 簇 cpu8-15，计时正本） | categraf | 无 | categraf `CPUAffinity=0-7`（X100 用户域）；**A100 cpu8-15 零监控进程** |
| **枢纽节点**（同宿主承载 acc/func） | evald `:8791`（X100 簇 cpu0-7，acc+func） | categraf | VictoriaMetrics `:8428` ＋ Nightingale `:17000` | categraf/VM/n9e `CPUAffinity=8-15`（该宿主计时已迁出，A100 空闲）；**X100 cpu0-7 留给 acc/func** |
| 浏览器（人） | 看大盘与告警 | — | — | `http://<枢纽节点>:17000`；过渡期 `dashboard.html?prom=http://<枢纽节点>:8428` |

**推荐映射**（P0 定案，板清单内一行可换 → U4）：**计时正本留在现宿主（10.18.60.100）不动，
新宿主承担 acc/func ＋ 枢纽**。理由：`/proc/set_ai_thread` 整簇注册（ADR-0012）、HMP/spine 计时栈、
计时锁分区（ADR-0014）构成的计时环境**零迁移**是本案最高价值的不变量；acc/func 车道按设计
不持计时锁、验收口径是正确性，抗噪余量更大（同宿主异簇下仍有共享内存带宽/缓存的耦合，见 R3，
以 P1/P3 实测判定）。

### 2.2 组件与落地参数

| 组件 | 版本 / 形态 | 落位 | 端口 / 绑定 | 持久化 |
|---|---|---|---|---|
| VictoriaMetrics | 单机版，**riscv64 自建**（R1） | 枢纽节点| `0.0.0.0:8428`（消费方是计时节点推送与 LAN 浏览器，非同机，故不能只绑 127.0.0.1） | `vmdata/`（retention 90d） |
| Nightingale | v9.x **riscv64 自建**（R1） | 枢纽节点| `0.0.0.0:17000`（计时节点推送目标 ＋ 浏览器入口） | `n9e.db`（SQLite 单文件）＋ 规则/大盘 JSON 导出入仓 |
| Categraf | v0.5.x riscv64 自建（R1） | 计时节点、枢纽节点| 无监听端口 | 无 |
| node_exporter | 现状 `:9100`（用户态 `~/ne`），P6 退役 | 计时节点、枢纽节点| `0.0.0.0:9100` | 无 |

> **不引入 MySQL/Redis**：n9e 轻量模式内置 SQLite（元数据）＋ miniredis（缓存/登录态/心跳态）。
> 生产化升级路径已留：etc 配置 `[DB]/[Redis]` 改外接即可，**部署形态仍是单二进制**。
> **不引入 vmagent/vmalert**：单机规模下 VM 自带抓取器过渡、告警由 n9e 承担。

### 2.3 数据面

- **指标**：categraf（两宿主）→ 枢纽节点`n9e :17000 /prometheus/v1/write`（写入代理）→ VM
  `/api/v1/write`；n9e 大盘/告警以 PromQL 查 VM。
- **心跳**：categraf `[heartbeat]` 10s → n9e Targets 在线态（v6 起无 `target_up`，失联以心跳超时判定）。
- **放行**（按源地址窄放行，不做全网开放）：计时节点→ 枢纽节点`:17000`；浏览器 → 枢纽节点`:17000`/`:8428`。
- **备选写径**（P1 记录、默认不用）：categraf 直写 VM `:8428/api/v1/write`，n9e 只读——
  少一跳，但代理写路径是官方组合形态且 agent 配置稳定（换后端不动宿主侧），维持默认。

## 3. 接缝（seam）

验收只在下列接缝上做；VM 存储引擎、n9e 任务调度等内部实现不进测试面。

| 接缝 | 定义 | 谁在它之上 | 已有 / 新建 |
|---|---|---|---|
| **S1 指标契约面** | PromQL 查询入口：序列名 ＋ 标签集合 ＋ 数值（Prometheus 同构 HTTP API） | `dashboard.html`、告警规则、对账查询、人 | **已有**（VM 原义复用，不新建） |
| **S2 部署单元边界** | 宿主上 systemd 单元状态 ＋ 板清单声明的文件（路径 ＋ md5） | 回退动作、md5 对账门、自启演练、部署幂等 | 已有（systemd）＋ 新建（板清单/部署清单） |
| **S3 推送链路观测面** | n9e Targets 在线态 ＋ VM 对推送样本的可见性 | 失联判定、写入代理验证 | 新建（宿主 → 宿主方向） |

S1 是最高接缝：**采集、存储、告警、面板四层全部通过它验收**，底层换 VM/n9e 或改钉核策略都不
改变测试靶心。不设接缝的：VM 磁盘格式、n9e 内部调度、SQLite schema（不做断言）。

## 4. 已定决策

| # | 决策 | 理由 / 边界 |
|---|---|---|
| D1 | 枢纽落宿主侧（枢纽节点本体），不引入常驻 x86 主机 | 消除开发机/容器宿主/端口转发一类宿主耦合；观测链路随宿主存活 |
| D2 | **板清单参数化**：板数量、角色、实例、`board` 与标签、采集器钉核、单元清单全部由清单声明 | spec 不写死「两块」；加板/换板只改清单不改代码 |
| D3 | 存储＝VictoriaMetrics 单机版，retention 90d | API 同构，面板与告警 PromQL 原义复用 |
| D4 | 可视化/告警/心跳＝Nightingale 单二进制轻量模式（内置 SQLite＋miniredis） | 不引入外部 MySQL/Redis；升级路径＝etc 外接，形态不变 |
| D5 | 指标语义不变：`node_*`、`evald_*` 与 `job`/`board`/`role`/`cores`/`clusters`/`workers` 标签语义原义保持 | 冻结面板与既有 PromQL 资产原样可用；对账才有基准 |
| D6 | `up` 兼容流＝宿主侧 exec 脚本（宿主侧闭环，无回程拉取） | 推送链路天然无抓取器 `up`（§8.3） |
| D7 | 采集 30s；告警 `for` 缺省 3m（队列族 2m）；级别映射 warn→Sev2、crit/失联→Sev1 | 与现状节奏一致，减少计时簇扰动 |
| D8 | 两宿主的 `clusters` 与 `workers` 字符串**保持同一取值** | 面板对 `up{job="boards"}` 是「末条命中」式读取（:1281-1293），两宿主串不同则核簇定义/核段命名漂移 |
| D9 | 新增物全部落 `monitor-next/`；现有 `monitor/*` 冻结原样 | 退路清晰：旧链路正本在退役前始终完整 |
| D10 | 七件冻结物逐字节零改动，md5 对账为最终证明 | 部署不变式是硬资产 |
| D11 | **计时环境零迁移**：计时节点上 evald 字节、单元、锁分区不变；监控栈不进计时节点的 A100 簇 | 计时正本与 ADR-0012/0014 不变量不可触碰 |
| D12 | 存储替换与采集替换解耦：先 VM 直抓并行对账，后 categraf 推送 | 两件事各自可独立回退，任一失败不牵连另一件 |
| D13 | 宿主侧动作集中在单个维护窗口，回退单元＝「停服务」（`systemctl stop categraf`） | 回退不需要改任何文件 |

## 5. 用户故事

### A. 采集面（宿主侧）

| # | 行为 | 可独立验证 |
|---|---|---|
| US-01 | 两宿主采集器按角色钉核：计时节点的 categraf 仅在 cpu0-7；枢纽节点的 categraf/VM/n9e 仅在 cpu8-15 | 两宿主 `systemctl show -p CPUAffinity` ＋ `ps -oL psr,comm` 采样；计时节点上无监控进程落在 cpu8-15 |
| US-02 | 采集器开机自启 | 宿主重启后 ≤60s 内 VM 可查到 `node_*` 与 `evald_*` 样本 |
| US-03 | 主机指标保真：面板在用清单里的 `node_*` 序列全部存在且与 node_exporter 同值 | 并行窗口内同一时刻的 `:9100/metrics` 与 VM 查询逐项比对（30s 采样错位按 §10 口径） |
| US-04 | 业务指标保真：`evald_*` 指标名与标签 100% 透传 | VM 查询得到的「序列名＋标签集合」与 evald `/metrics` 直读相等 |

## 7. 告警规则映射（9 族）

级别统一映射：warn（面板黄）→ n9e Sev2；crit（面板红）/失联 → Sev1。`for` 缺省 3m，队列族 2m。
通知渠道 P4 时由用户指定（U1）。**新拓扑下每条族表达式均需按 `board` 分组或按实例生成**——
两宿主的同名指标是两台机器，跨宿主 `avg`/`max` 会把两台机器的读数混成一个（旧单宿主 spec 无此约束）。

| 族 | 级别 | PromQL 草案（迁后口径） | 备注 |
|---|---|---|---|
| 主机失联 | Sev1 | n9e 心跳超时（Targets 离线事件）；PromQL 兜底 `absent(node_uname_info{job="boards",board=~"K3|K3-ACC"})` | 心跳断≠数据断，双口径并存（US-19） |
| evald 实例离线 | Sev1 | `absent(evald_up{job="evald",board=~"K3|K3-ACC"})`，按板清单逐实例生成一条 | 描述里附 acc 实例疑触 `MemoryMax` 的排障指引 |
| 温度 | Sev2 / Sev1 | `max by (board) (node_hwmon_temp_celsius{job="boards"}) ≥ 70 / 85` | |
| 簇均核占用 | Sev2 / Sev1 | X100 簇：`100*(1-avg by (board)(rate(node_cpu_seconds_total{job="boards",cpu=~"0\|1\|2\|3\|4\|5\|6\|7",mode="idle"}[2m]))) ≥ 80/92`；A100 簇同式 `cpu=~"8…15"` | 按板成对生成（计时节点与枢纽节点的 X100 是两台机器，不可合并）；`clusters` 标签是面板展示串，不做选择器 |
| swap | Sev2 / Sev1 | `100*(1-node_memory_SwapFree_bytes/node_memory_SwapTotal_bytes) ≥ 60/80` | 前置 `node_memory_SwapTotal_bytes > 0`（无 swap 不触发） |
| 内存 | Sev2 / Sev1 | `100*(1-node_memory_MemAvailable_bytes{job="boards"}/node_memory_MemTotal_bytes) ≥ 80/92` | 按 `instance`（＝宿主）分组 |
| 硬盘 | Sev2 / Sev1 | `100*(1-node_filesystem_avail_bytes/node_filesystem_size_bytes{fstype!~"tmpfs\|overlay\|squashfs"}) ≥ 80/92` | 按 `instance, mountpoint` 分组 |
| 风扇 fault | Sev1 | `max by (board) (node_hwmon_fan_fault{job="boards"}) ≥ 1` | |
| 队列 | Sev2 / Sev1 | `sum by (board) (evald_queued{job="evald"}) ≥ 20/50` | `board` 依赖 §8.2 注入；未注入前以 `instance` 分组 |

**屏蔽规则**：① 计时敏感天窗（手工基准/全量验收时段）；② 宿主侧维护窗口。这是现状没有的能力，
也是本次改造最直接的日常收益之一。

### 8.1 指标命名决策

| `role` / `accent` / `cores` | 同上 | `纯计时 · A100 簇` / `timing` / `8-15` | `acc 0-5 / func 6-7 · evald-acc 单元` / `acc` / `0-7` |

| `job="boards"` / `job="evald"` | `[global.labels]` ＋ 实例 labels ＋ `up` 兼容流 | 必须保持（面板/告警选择器锚点） | 同左 |

### 8.3 `up` 兼容流（推送链路的固有缺口）

推送链路没有抓取器，天然不产 `up`；而冻结面板的在线判定、`clusters`/`workers` 读取都挂在
`up` 上（§1.5 第 2 条）。P3 以 **exec 插件脚本**每 30s 输出下列序列补齐：

```
# 计时节点
up{job="boards",board="K3",clusters="X100:0-7,A100:8-15",workers="<两宿主同串>",fleet="k3"} 1
up{job="evald",board="K3",role="纯计时 · A100 簇",accent="timing",cores="8-15",instance="<计时节点>:8788"} 1

# 枢纽节点（acc/func 同宿主）
up{job="boards",board="K3-ACC",clusters="X100:0-7,A100:8-15",workers="<两宿主同串>",fleet="k3"} 1
up{job="evald",board="K3-ACC",role="acc 0-5 / func 6-7 · evald-acc 单元",accent="acc",cores="0-7",instance="<枢纽节点>:8791"} 1
```

脚本自带可达性检测（curl 本宿主 `/metrics` 端点），失败则该序列发 0 或停发 → `up` 语义比「进程
活着就答」更接近真实。备选：VM 侧加 up-only 极简抓取任务（metric_relabel 丢弃全部目标样本）；
exec 方案宿主侧闭环、无回程拉取，优先。

## 10. 测试决策

- **主接缝＝S1**：所有验收以 PromQL 查询结果为判据，不读 VM/n9e 内部状态、不对 SQLite 断言。
- **对账窗口**：数值类并行采集 ≥7d；抽样时刻允许 30s 采样错位——取同刻或 ±1 tick；计数类一律用
  `increase()` 在同一时间窗内对齐后比较，不做瞬时点值比较。
- **门禁脚本化**：md5 对账、单元状态检查、一组固定 PromQL 存在性/数值断言，构成 P2/P3/P6 门的
  可执行判据（S2 ＋ S1 两个接缝，不新增第三个）。
- **演练清单**：告警触发与恢复（US-16）、屏蔽静默（US-18）、枢纽节点重启自启（US-12）、
  采集器回退（US-07）、部署幂等与自动回滚（US-25/26）。
- **完成定义**：见 §14 DoD 清单全绿，且 §4 各决策在实现与文档中无偏离。

### 附 A：部署通道讨论稿（U2 的原始分析）

> P3（categraf 上宿主）与宿主恢复后的回归门都需要一条**幂等、可验证、可回退**的部署通道。
> 当前倾向：**repo 原生清单式部署器**（基于 `ops/pssh.py`）先行，ansible 作多宿主化升级路径，
> opentofu 不适用。**板清单参数化（D2）与本节同源**——清单即目标状态，加板只改清单。

| 方案 | 适用性判断 | 结论 |
|---|---|---|
| OpenTofu / Terraform | 面向云厂商 API 的状态机（provision＋state）；无裸机 SSH 一等支持（社区 ssh provider 停维护，把 SSH 当 CRUD 属反模式） | **不适用**：K3 是已存在资产，需要配置管理（configure）而非资源供给（provision） |
| Ansible（控制节点） | 单/双宿主用不上其核心收益（并行 fleet／inventory／模块生态）；宿主上 `python3` 已具备（evald 依赖）；控制节点若落开发机则引入额外宿主依赖 | **升级路径**：多宿主 fleet（K1 四板回归一类）时启用；届时把清单翻译成 playbook 成本低 |
| **repo 原生清单式部署器** | `ops/deploy.py` ＋ 声明式 manifest，复用 `ops/pssh.py`（paramiko）通道 | **先做**：零新依赖，与仓库哲学（纯 stdlib／md5 对账／selftest 门禁）同构 |
| pull 式自部署（宿主上 cron/systemd timer 拉正本执行） | 宿主主动拉取执行 | **不作常态通道**：宿主上须持凭据，且变更时序不受控（可能撞计时互斥窗口）；仅可作只读文档同步 |

`ops/deploy.py` 设计要点（单宿主 mini-ansible 量级，约 200 行）：

1. **manifest 即目标状态**：`boards[]`（宿主身份、角色、钉核）／`instances[]`（board 标签、端口、
   语义标签）／`files[]`（仓内源 → 宿主上路径 ＋ 期望 md5，与 CHANGELOG 冻结清单同源）／
   `units[]`（systemd 单元）／`cron[]`／`dirs[]`；
2. **幂等执行**：读宿主侧现状 → 只推差异 → 推送前打时间戳备份 → 写后 md5 复验；
3. **门禁钩子**：hooks 串（`evald.py --selftest`、categraf 配置自检、`ev.py run --op add` 金丝雀），
   任一失败自动回滚到本次备份目录；
4. **首个用户 ＝ P3**：categraf riscv64 二进制 ＋ conf ＋ 单元进清单，部署即验证、不过即回退——
   与 P3 的回退语义（`systemctl stop categraf`）互补。
