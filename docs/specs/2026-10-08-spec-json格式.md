## 1. 定义的职责

`spec.json` 是集合与用例合同：定义“调用哪个算子，传什么输入和属性，预期返回什么，用什么规则检查”。它供输入构造、正确性检查与服务端适配共用。调用适配器承担 torch/FlagGems 的实际解析、布局适配和执行，spec 只保存可解析的标识与数据，不嵌入 Python 代码或 shape 表达式。

采用“集合 → 算子 → 用例”三层。算子层承载稳定调用方式与返回项名称；用例层完整保存输入、属性、输出及检查。用例不继承其他用例，运行前不依赖隐式默认值，增加 dtype 变体也不会覆盖另一个用例的容差。多输入列表属于单次调用，多个 `cases` 才表示不同测量。

条目注册、执行环境与运行结果各有正本：spec 的 `entry_ref` 引用条目注册记录，当前未审计时为 null；它不包含 `track`、`dev_flag` 或条目态。运行时版本、主机、warmup/rep、超时、实际输入摘要和结果留在运行记录，不将“某次已通过”写回用例定义。

不公开测试用例单独放入 `spec.hidden.json`，使用 [独立隐藏格式](2026-10-08-spec-hidden-json格式.md)。隐藏文件只引用本 spec 已定义的算子与检查合同，不能增加或重定义算子；公开 spec 不依赖隐藏文件即可校验和分发。

## 2. 顶层字段

| 字段 | 意义 |
|---|---|
| `$schema / schema_version` | 本地 `spec.schema.json` 路径与格式版本；接受 2.0.0/2.1.0，Schema 的 `$id` 为 `urn:rvbench:spec:2.1.0`，消费者拒绝未知版本 |
| `version` | 本文件自身内容版本；当前 0.3.1，与格式版本分别管理 |
| `suite` | 集合 ID、标题、draft/ready、目标硬件，以及当前 scope 与计划总量 |
| `sources[]` | 来源标识、位置、版本和版本完整性；来源版本与运行版本分别记录 |
| `policies` | 同一输入复用、禁止隐式覆盖 shape/dtype、未判定不得算通过、调用级计时合同 |
| `operators[]` | 算子声明及其用例 |
| `baseline` | 2.1.0 的可选基准包：代码清单、命令和历史测速引用；不改变用例检查合同 |

`schema_version` 与顶层 `version` 均为必填，前者须为 Schema 支持的版本，2.0.0 不允许 baseline 字段；后者是文件自身的内容版本。版本采用无前导零的 `MAJOR.MINOR.PATCH` 三段非负整数，不接受 `latest`、浮点数或省略字段。改变输入、属性、输出、检查、来源或 baseline 时更新 `version`；结构或格式语义改变时更新 `schema_version`，内容完全相同也须由摘要确认，不能只比较版本字符串。

本次将原 v1 的 `suite.version` 移至顶层，属于结构不兼容变更，因此公开格式升至 **2.0.0**，实例内容升至 **0.2.0**。不接受双版本字段或隐式迁移旧文件；旧输入须显式转换、重新校验并重算引用摘要。独立隐藏格式未改变结构，仍为 1.0.0；两个 Schema 版本无须相等。当前公开实例仍是 draft，不因升版变为可执行集合。

运行记录使用独立 [eval_results.json 格式](2026-10-08-eval-results-json格式.md)，保存 spec 的 `schema_version`、`version` 与 canonical 内容摘要，不把评测状态写回 spec。

`planned_case_count=80` 表示设计目标；实际定义数从 `operators[].cases[]` 计算，当前为 8。没有给尚未落地的 72 条创建空壳，也不宣称已经有 80 个可运行作业。

## 3. 算子与调用

| 字段 | 意义 |
|---|---|
| `id / display_name` | 规范标识与展示名；Flash 的 ID 保留 `_flash_attention_forward` |
| `entry_ref` | 注册正本中的条目引用，暂未审计为 null；不建立第二套注册表 |
| `classification` | 来源文档的层级/家族与依据；不自动覆盖正式面板分级 |
| `call.args / call.kwargs` | 实参位置与关键字名，绑定到用例的具名 input 或 attr |
| `call.implementations` | candidate 与 reference 的 callable/adapter 标识；两侧共享同一逻辑实参合同 |
| `returns` | tensor 或 tuple；有序返回槽位名称 |
| `cases[]` | 独立用例合同 |

例如 Softmax 的 `args` 明确绑定 x、dim、half_to_float，参考符号为 `torch.ops.aten._softmax.default`。Conv2D 的 x、weight、bias 为有序实参，stride/padding/dilation/groups 为关键字。注意力参考为 `attention_math_v1` adapter，表示规划中的定长数学参照，不表示此实现已经存在。

resolver 只能执行其已实现的符号/adapter，无法解析时报告待接入，不能退回别的 shape 或 dtype。Schema 校验符号是数据字符串，校验器不导入 torch/FlagGems，也不执行这些字符串。目标版本是否真的接受声明签名由 M2 探针验证。

## 4. 用例字段与生成语义

| 字段 | 意义 |
|---|---|
| `id / slot` | 全局唯一 ID：`suite.operator.Cxx`；同算子槽位唯一 |
| `inputs[]` | 每个实参独立具名，kind、shape、dtype、layout 与 generator |
| `attrs` | 完整参数值，包括显式 false、0 与 null；不允许漏传绑定的属性 |
| `outputs[]` | 与 returns 同序的预期类型/shape/dtype/layout，或带理由的 pending 项 |
| `verification` | 每返回项恰有一个检查方法，另列跨输入/输出的语义规则 |
| `execution` | pending_probe / ready / blocked / skip；原因与支持性证据 |
| `provenance` | 来源 ID、原用例位置、source_typical/derived 以及归一化说明 |

### 4.1 Tensor、None 与布局

`kind=tensor, shape=[]` 是零维标量；shape 中的 0 表示空维。`kind=none` 是显式 None 实参，例如后续 Conv2D 的 bias=None，没有 dtype 或 generator；两者不混淆。v1 只定义 tensor/None 输入、tensor/tuple 返回；输入列表、字典返回与其他标量签名需要后续格式扩展。

`layout.axes` 按 shape 维序列出语义轴。`contiguous` 根据 shape 计算行主序 strides，storage_offset=0；`strided` 显式声明非负 strides，可填写非负 storage_offset（省略为 0）。其构造器先分配足够底层存储再建立 view，不能先 `.contiguous()` 改写合同。axes/strides 长度必须匹配 rank；v1 不定义跨输入共享存储或负 stride。

输入 layout 是构造要求。输出 layout 表示适配后检查的逻辑布局，适配器须保留实际 layout 记录；是否额外转置/裁剪以及成本归属按绑定计时合同处理，不能凭 layout 字段自动把适配成本排除。

### 4.2 生成器

初版的 `torch_cpu_uniform_v1` 使用每输入独立 CPU `torch.Generator`，以该输入 seed 初始化；先生成 fp32 均匀样本 `u∈[0,1)`，按 `low + (high-low)*u` 缩放，再转换为声明 dtype，最后构造声明 layout。range 描述转换前的范围，dtype 量化可能改变端点；不得误用默认 randn。非连续输入按底层存储的顺序生成再建立 view。

`constant_v1` 使用声明 value 填充，供零输入与平局档扩展。生成器标识是版本化合同，尚未实现运行构造器；运行端不支持时必须拒绝该 generator，而非自行猜实现。相同 seed 在不同 torch 版本不承诺逐位一致，运行记录须绑定 torch 版本和每输入实际内容 SHA-256；两侧始终复用同一次物化输入。

## 5. 检查与数值合同

| 检查方法 | 定义 |
|---|---|
| `exact_values` | 对齐 shape/dtype 后精确数值相等；有限浮点的 +0/-0 视为数值相等，不是 bitwise 模式；整数不转 float |
| `allclose` | 由绑定数值合同提供 rtol/atol 与特殊规则；未绑定时记 pending，不使用服务端默认宽松容差 |
| `topk_values` | sorted=true 时精确比较有序选择值；sorted=false 时比较值多重集合 |
| `topk_indices` | int64、范围、每行不重复、gather 与 values 精确对应；不与参考平局索引强制相等 |
| `pending` | 明确未定的输出合同；原因必填，不能算通过 |

`softmax_probability_v1` 额外检查有限性、非负与沿 dim 归一化，其归一化误差阈值单独绑定合同。`topk_selection_v1` 额外检查第 k 大/小阈值与选择值多重集合合法性，防止仅有合法索引却没有真正选出 TopK。

当前 Abs/Aminmax 使用精确数值检查，TopK 使用值与索引语义检查；Softmax/Mv/Mm/Conv2D/Attention 数值合同未裁决，显式 `status=pending`。±0 的位模式扩展档需先完成 M2 裁决，v1 C01 不自行发明位一致要求。

数值/计时合同只有一个正本。`contract` 为 pending（reason）或 resolved（相对本 spec 的 path 与整个正本文件的 sha256）。可以绑定现有 `numeric-contract.csv`，由消费该检查的 op、输出 dtype 与特殊规则定位合同行；如果同一 op/dtype 对应多个无法唯一选取的范围，则拒绝解析并升级合同格式，不能随机取一行。归一化规则按绑定正本的对应条款解释。

校验器验证 resolved 引用的本地文件存在与摘要一致，不解释其 rtol/atol 或判定裁决是否正确；数值适配器必须再解析正本并检查所需规则齐全。没有正式数值正本时保留 pending，不能填一个“看起来合理”的 fp16 阈值。

Flash 的五元组全部保留。out 已知 shape/dtype，lse/seed/offset/p 的目标版本合同尚未确认，因此四项均为 pending。后续只能用固定版本证据补全；无 dropout 时的占位输出可用专门 validity 检查表达，不能直接删掉。v1 尚不包含该检查模式，需要在明确语义后扩展 Schema 与消费者。

## 6. 定义有效、可验收与实际通过

定义有效：Schema 与跨字段约束通过。可验收：集合声明 ready、C01 均有支持性证据，且没有 pending 输出/检查/合同。实际通过：运行环境已锁定、适配器可解析、完整检查规则执行成功，结果证据齐备。三者分别报告。

`execution.ready` 表示支持性探针已证明可接入，需要 evidence；blocked/skip 都需要具体原因与证据。C01 被 skip 时不能将典型 8 算子集宣称为可验收；扩展档 skip 也不算通过。draft 的 case 仍可交给独立探针，但不能绕过正式验收门禁。

运行前须另记录集合内容摘要、绑定合同摘要、候选代码摘要、实际 FlagGems/torch/triton/evald 版本、backend/host/设备、adapter/generator 版本、warmup/rep/同步/超时。运行后逐项记录实际输入 shape/dtype/strides/内容摘要、attrs、返回结构与逐输出检查，以及 job_id、延迟、误差、终态。来源文档的短 commit 不充当实际运行版本。

校验器的 `--require-ready` 仅检查定义的完整性门禁，不提供执行器，也不能代替真实支持性探针和数值合同解析。初版的预期是“定义校验通过、可验收校验失败”，明确显示仍待 M2/M3 的工作。

## 7. 使用与验证

Rust 构建及本地验证（2026-10-14 更新）：

```powershell
cargo build --workspace --locked
cargo run -p rvbench-cli -- validate spec examples/hello-world/spec.json
cargo run -p rvbench-cli -- validate spec examples/hello-world/spec.json --require-ready
cargo test --workspace --locked
```

普通校验成功退出 0；结构/语义错误退出 1；`--require-ready` 遇到 pending 等门禁退出 2。工具计算整个 spec 的 SHA-256：对解析后的 JSON 排序键、紧凑序列化为 UTF-8；不含空白格式差异。它是本项目 v1 的摘要算法，不宣称采用通用跨语言 canonical JSON 标准；其他语言需实现同一规则后比对固定测试样本。

校验分两层：Schema 检查字段、类型、枚举及未知字段；语义校验检查唯一 ID、引用绑定、布局 rank、返回项覆盖，以及这 8 个算子的归约/收缩维、卷积尺寸、TopK 索引 dtype、注意力序列长度与布局。其他算子可使用通用结构，但增加算子时还需增加相应语义验证与运行 adapter。

JSON 重复键、非有限数值、silent shape/dtype fallback 均不属于可接受合同。回归测试包含导致基准误测的负例与格式合法的 None/scalar 正例，不依赖板上设备。

## 8. 后续接入

1. M2 固定真实调用、版本与支持性，补注意力输出合同；保留失败证据。
2. M3 实现 generator/reference/check adapter，绑定数值与计时正本；补 C02–C10，将集合内容版本更新。
3. M4 服务端按 spec 用例构造实际调用，结果回显完整合同，禁止通过旧 shape 列表丢失多输入或属性。
4. M5 扩展用例全量处置和 C10 复测；既有条目注册与候选结果词表继续由各自正本管理。

本次已交付格式、首份 8 用例实例、校验工具与测试；没有实现测量执行器，没有上板，也没有把 fp16 容差或历史条目状态标成已完成。
