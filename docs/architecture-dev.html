监控改造目标架构 — VictoriaMetrics × Categraf × Nightingale

本页是监控技术栈改造的目标架构蓝图（未实施）：时序记录迁 VictoriaMetrics， 板端采集迁 Categraf，可视化大盘与告警迁 Nightingale（夜莺）。 三大硬约束贯穿全图：evald 零改动（字节冻结 7 件一个字节不动）、 数据方向反转可回退（拉模式并行双跑后再切推送）、既有 PromQL 资产复用 （指标名与 job 标签语义保持）。实施计划与验证门见 spec.md；现状架构见 architecture.html §06。

01现状 → 目标

现状（architecture.html §06 ＋ monitor/README.md）： 板上 node_exporter（:9100 用户态）与 evald 双实例（:8788/:8791 原生 /metrics）由 Windows Docker 里的 Prometheus（容器 k1-prom :9090）每 30s 拉取； 可视化＝零依赖单文件 dashboard.html（file:// 直开，浏览器直查 Prometheus）； 告警全部由面板前端计算——浏览器不开着就没有告警，无通知渠道、无屏蔽窗口、无历史。 目标架构把「采集 / 存储 / 可视化 / 告警」四层各自换成专用组件，数据方向由拉改为推。

02目标拓扑

板端只新增 Categraf 一个进程（X100 用户域，与现 node_exporter 同侧，不触碰 A100 计时簇）； Windows 侧监控枢纽＝VictoriaMetrics（容器）＋ Nightingale（WSL2 单二进制，与 k1-prom 同机）， n9e 轻量模式内置 SQLite＋miniredis、零外部 MySQL/Redis。 数据方向反转是最大变化：板端推、枢纽收——因此 P0 必须先验证 K3 → 枢纽 :17000 的网络可达 （现状只有 Windows → 板的拉取方向；n9e 落 WSL2，还需 mirrored／portproxy 放通）。

实线＝常态数据流；虚线＝心跳 / 查询 / 过渡期路径；灰虚框＝退役项（P6）。
颜色：青＝板端新增（Categraf）· 蓝＝Nightingale 枢纽 · 紫＝VictoriaMetrics / 用户侧 · 绿＝零改动资产。 端口：:8788/:8791 evald 原生 metrics（冻结）· :17000 n9e·WSL2（mirrored／portproxy 放通，P0 验证方向） · :8428 VM（本机 + dashboard 过渡读）。

03指标流与标签契约

三条指标流汇入 VM：主机流（node_*，Categraf 自采）、业务流（evald_*，Categraf 抓取透传）、 兼容流（up 序列，exec 补齐）。标签契约的第一目标＝既有 dashboard.html 查询与告警 PromQL 原样可用——它的选择器是 {job="boards"} / {job="evald"}， 并从 up 序列读 clusters/workers 静态标签（dashboard.html:1280-1293）。

04采集面 · Categraf

位置与形态

K3 板 X100 用户域（cpu0-7），systemd 常驻（kategraf.service，CPUAffinity 钉用户域核）， 与现 node_exporter 同侧；不触碰 A100 计时簇 cpu8-15。interval=30s 与现状抓取节奏一致 （计时敏感扰动已获用户确认的口径不变）。

插件选择：node_exporter 输入 决策

板端用 input.node_exporter（内嵌官方采集逻辑，node_* 100% 兼容）而非 Categraf 原生 cpu/mem/disk 套件——保住既有查询/告警资产与 hwmon 温度风扇覆盖。官方明确两者二选一，同机混开＝重复采集。 Windows 监控主机自监控可用原生套件（n9e 内置主机大盘即插即用）。

evald 抓取：prometheus 输入

两个 instance 分别抓 127.0.0.1:8788 / :8791 的 /metrics， 免 token（原生 exposition 本就免 token）。evald 零改动——这是本方案对字节冻结不变式的根本尊重。

riscv64 交付 最大风险

Categraf 官方发布物只有 linux/amd64、linux/arm64、windows——无 riscv64。 路径：Go 交叉编译（GOOS=linux GOARCH=riscv64 CGO_ENABLED=0）， 用 build tags 裁掉 CGO 依赖插件（oracle 等）。P3 先做编译＋上板 spike，不过门则维持 VM 直抓（P2 形态长期化）。

Why：这是全案唯一可能推翻既定拓扑的点，故列为 P3 硬门禁而非假设。

上报与心跳

[[writers]] 单写址 http://<win-host>:17000/prometheus/v1/write （支持 basic_auth/timeout 等）；[heartbeat] 10s 报 /v1/n9e/heartbeat → n9e「监控对象」在线态与机器元数据。心跳断≠数据断：告警以数据序列 absent 兜底。

回退

systemctl stop categraf 即回到 VM 直抓形态（P2 长期化）；板上 node_exporter 文件与 crontab 保留到 P6 才注释，任何时刻可恢复原拉模式（恢复 k1-prom 也只是 docker start）。

05存储与查询面 · VictoriaMetrics

单机版选型

本规模（1 板 + 2 evald 实例，~1.6K 序列 @30s）用单二进制单机版绰绰有余； vmagent/vmalert/vmcluster 全部不引入（拉模式由 categraf 承担、告警由 n9e 承担）。 官方 quickstart 的 n9e 组合数据面（VM＋n9e＋categraf）与本蓝图一致；其 mysql＋redis 部分不采纳——n9e 单二进制轻量模式不需要它们。

关键参数

-storageDataPath=/vmdata（docker 卷）；-retentionPeriod=90d （现状 Prometheus 缺省 15d，升到 90d 仍 <1GB）；镜像 tag 在 P1 拉取时固定为当周 stable，不追 latest。 端口绑 0.0.0.0:8428（供 n9e/WSL2 数据源访问——k1-prom 的 127.0.0.1 绑定不可复用）。

API 同构＝过渡桥

VM 原生服务 /api/v1/query、/api/v1/query_range 等 Prometheus 查询 API——dashboard.html 只用这两个端点（dashboard.html:921 的抓取面）， ?prom=http://127.0.0.1:8428 理论上零改动可用；file:// null origin 的 CORS 放行在 P2 实测（R3）。

P2 并行直抓

VM 自带抓取器：-promscrape.config 直接吃 Prometheus 语义的配置 （宽容解析）。把 monitor/prometheus.yml 复制为 monitor-next 内的新文件挂给 VM （原文件冻结不动），k1-prom 与 VM 双跑对账 ≥7 天——这一步让「存储替换」与「采集替换」解耦，各自可独立回退。

06可视化与告警面 · Nightingale

n9e 是枢纽里唯一的「人界面」：大盘、告警规则、屏蔽、值班、用户权限全在 Web UI； 对数据面它只做两件事——代理写（categraf → n9e :17000 → VM）与查询（PromQL → VM）。 部署形态＝单二进制：官方 linux-amd64 tarball（无 Windows 原生包）落 WSL2 systemd 常驻， 轻量模式内置 SQLite＋miniredis，解压即启、零外部 MySQL/Redis。 v6 起 n9e 不再生成 target_up 指标，机器失联以心跳超时判定（Targets 页在线态）， PromQL 层以 absent() 兜底。

为什么单二进制

现栈（k1-prom＋dashboard.html）零状态件，四容器对单板监控是重步；轻量模式只净增一个进程＋ 一个 n9e.db，运维重量与现栈同量级。官方二进制部署文档自带 systemd 示例； 升级路径＝etc 配置改外接 MySQL/Redis（多实例 HA 同路），部署形态不变。

代价（已接受）

miniredis 内存态：重启丢登录态（重登）与心跳态（分钟级重建）；SQLite 单文件： 灾备＝文件备份＋规则/大盘 JSON 导出入仓。官方将轻量模式定位为测试/体验，生产建议外接 MySQL/Redis——单用户单板场景接受，扩容路径清晰。AI 助手功能需真 Redis Streams（不用，不受影响）。

07迁移路径（P0–P6）

每阶段独立可回退、有硬验证门；板端动作集中在 P3 一次完成，其余阶段全部发生在 Windows 侧。 详细动作清单、验证门与回退手段见 spec.md §7。

  1. 前置确认（零改动） K3 → 枢纽 :17000 端到端可达（先定 WSL2 网络模式：mirrored 优先、portproxy 兜底）· 防火墙放行 · WSL2 就绪（systemd）· Docker 资源余量 · 冻结物 md5 复核
  2. 枢纽骨架（纯 Windows 侧） WSL2 装 n9e 官方 tarball（解压即启：SQLite＋miniredis 内置，零外部状态件）＋ systemd＋任务计划自启链 · VM 容器改绑 0.0.0.0:8428 · n9e 配 VM 为默认数据源＋写入代理 · 建用户/业务组 · 门禁：板→:17000 端到端、UI 可查 VM 样本、重启自启
  3. 存储并行（板零改动） VM 以 -promscrape.config 直抓三目标（复制 prometheus.yml 语义）· k1-prom 与 VM 双跑 ≥7d · dashboard.html ?prom=:8428 只读并行 · 门禁：指标对账＋CORS 实测
  4. Categraf 上板（唯一板端阶段） riscv64 交叉编译 spike → systemd 部署 → node_* / hwmon / evald_* / 标签注入 / up 兼容流逐项对账 · 门禁：与 P2 数据并排一致、扰动 vmstat 对比无恶化 · 回退：stop categraf 即回 P2
  5. 告警上线（能力新增） 9 族规则录入 n9e ＋ 通知媒介 ＋ 计时天窗屏蔽 · 门禁：停 evald-acc 演练离线告警、手动 PromQL 回放验证阈值族
  6. 大盘重建 四层大盘在 n9e 逐层落地（漏斗→堆叠柱）· 门禁：与 dashboard.html 并排对数一致后才谈退役
  7. 退役收尾（逐项独立回退） VM 直抓任务撤 · k1-prom 容器封存（卷留 30d）· 板上 node_exporter 停用（crontab 注释、文件保留）· dashboard.html 归档只读 · monitor-next/README 记录接替关系
