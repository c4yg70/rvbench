监控改造目标架构 — VictoriaMetrics × Categraf × Nightingale

本页是监控技术栈改造的目标架构蓝图（未实施）：拓扑前提是两块 K3 板——一块专责 perf 计时测试，另一块承担 acc、func 与监控/面板组件；时序记录迁 VictoriaMetrics， 板端采集迁 Categraf，可视化大盘与告警迁 Nightingale（夜莺），枢纽整体落在板侧。 三大硬约束贯穿全图：evald 零改动（字节冻结 7 件一个字节不动）、 数据方向反转可回退（拉模式并行双跑后再切推送）、既有 PromQL 资产复用 （指标名与 job 标签语义保持）。实施计划与验证门见 specs/2026-09-20-监控栈改造.md； 现状架构见 architecture.html §06。

01现状 → 目标

现状（architecture.html §06 ＋ monitor/README.md）： 板上 node_exporter（:9100 用户态）与 evald 双实例（:8788/:8791 原生 /metrics）由开发机上的 Prometheus（容器 k1-prom :9090，绑 127.0.0.1）每 30s 拉取； 可视化＝零依赖单文件 dashboard.html（file:// 直开，浏览器直查 Prometheus）； 告警全部由面板前端计算——浏览器不开着就没有告警，无通知渠道、无屏蔽窗口、无历史。 目标架构把「采集 / 存储 / 可视化 / 告警」四层各自换成专用组件，数据方向由拉改为推， 枢纽从开发机迁到板侧（第二块 K3 板），观测链路不再依赖任何开发机/容器宿主。

02目标拓扑

两块 K3 板按角色分工（物理映射由板清单声明，推荐＝计时正本留现板、新板承接 acc/func ＋ 枢纽）： 板 P 计时板只跑计时与一个钉在 X100 用户域的 Categraf（A100 cpu8-15 零监控进程）； 板 A 承担 acc/func，并把 VictoriaMetrics ＋ Nightingale 一起装在本板、钉在 A100 簇 （该板计时已迁出，A100 空闲），X100 cpu0-7 完整留给 acc/func 车道。 数据方向反转是最大变化：板端推、板 A 收——P0 必须验证板 P → 板 A :17000 的可达性 （现状只有开发机 → 板的拉取方向）。枢纽是板上的 systemd 服务，n9e 轻量模式内置 SQLite＋miniredis、零外部 MySQL/Redis，全案无 WSL2、无端口转发、无容器宿主依赖。

实线＝常态数据流；虚线＝心跳 / 查询 / 过渡期路径；灰虚框＝过渡项或退役项（P6）。 颜色：青＝板端采集（Categraf）· 蓝＝Nightingale 枢纽 · 紫＝VictoriaMetrics 与用户侧 · 绿＝零改动资产。
跨板方向为本蓝图新增：板 P → 板 A（remote write ＋ 心跳）；枢纽与存储均在板侧，不再依赖开发机。 端口：:17000 n9e · :8428 VM · :9100 node_exporter（P6 停用）· :8788/:8791 evald 原生 metrics（冻结）。

04采集面 · Categraf

位置与形态

两板各一个 Categraf，systemd 常驻、按角色钉核：板 P 钉 X100 cpu0-7（与现 node_exporter 同侧，A100 计时簇 cpu8-15 零监控进程）；板 A 钉 A100 cpu8-15（该板计时已迁出，监控不得占用 X100 的 acc/func 车道）。interval=30s 与现状抓取节奏一致（计时敏感扰动的既有口径不变）。

插件选择：node_exporter 输入 决策

板端用 input.node_exporter（内嵌官方采集逻辑，node_* 100% 兼容）而非 Categraf 原生 cpu/mem/disk 套件——保住既有查询/告警资产与 hwmon 温度风扇覆盖。官方明确两者二选一，同机混开＝重复采集。 本次无板外被采集对象（开发机只充当浏览器），故原生套件不启用。

evald 抓取：prometheus 输入

两个 instance 分别抓 127.0.0.1:8788 / :8791 的 /metrics， 免 token（原生 exposition 本就免 token）。evald 零改动——这是本方案对字节冻结不变式的根本尊重。

riscv64 交付 最大风险

自建范围＝三件：Categraf（官方发布物只有 linux/amd64、linux/arm64、windows）、 VictoriaMetrics 与 Nightingale（官方发布物为 linux amd64/arm64，riscv64 情况未核实）。 优先在板上原生构建（Bianbu 自带 riscv64 工具链，天然规避交叉编译坑）， 交叉编译（GOOS=linux GOARCH=riscv64 CGO_ENABLED=0 ＋ build tags 裁掉 CGO 依赖插件）作备选。三件未就位不进入 P1。

Why：riscv64 自建是唯一可能推翻本拓扑的点（R1），故前移为 P0 硬门禁； 任一件不过门 → 重开 spec，不改投开发机/容器宿主或端口转发式折中。

上报与心跳

[[writers]] 写址 http://<板 A>:17000/prometheus/v1/write （支持 basic_auth/timeout 等）；[heartbeat] 10s 报 /v1/n9e/heartbeat → n9e「监控对象」在线态与机器元数据。板 A 上的 categraf 走本机 localhost，板 P 走 LAN。 心跳断≠数据断：告警以数据序列 absent 兜底。

回退

两板 systemctl stop categraf 即回到 VM 直抓形态（P2 长期化）；板上 node_exporter 文件与 crontab 保留到 P6 才注释，任何时刻可恢复原拉模式（恢复 k1-prom 也只是 docker start）。

05存储与查询面 · VictoriaMetrics

单机版选型

本规模（2 板 + 2 evald 实例，~1.6K 序列 @30s）用单二进制单机版绰绰有余； vmagent/vmalert/vmcluster 全部不引入（拉模式由 categraf 承担、告警由 n9e 承担）。 官方 quickstart 的 n9e 组合数据面（VM＋n9e＋categraf）与本蓝图一致；其 mysql＋redis 部分不采纳——n9e 单二进制轻量模式不需要它们。

关键参数

-storageDataPath=<本机目录>/vmdata（板 A 本地盘，无容器卷）； -retentionPeriod=90d（现状 Prometheus 缺省 15d，升到 90d 仍 <1GB）； 版本与产物 md5 在 P0 自建后锁定。端口绑 0.0.0.0:8428——消费方是板 P 的写入与 LAN 浏览器，非同机，故不能只绑 127.0.0.1。

API 同构＝过渡桥

VM 原生服务 /api/v1/query、/api/v1/query_range 等 Prometheus 查询 API——dashboard.html 只用这两个端点（dashboard.html:921 的抓取面）， ?prom=http://<板 A>:8428 理论上零改动可用；file:// null origin 的 CORS 放行在 P2 实测（R3b）。

P2 并行直抓

VM 自带抓取器：-promscrape.config 直接吃 Prometheus 语义的配置 （宽容解析）。把 monitor/prometheus.yml 复制为 monitor-next 内的新文件挂给 VM （原文件冻结不动），直抓两板三目标（:9100/:8788/:8791），与旧链路双跑对账 ≥7 天——这一步让 「存储替换」与「采集替换」解耦，各自可独立回退。

06可视化与告警面 · Nightingale

n9e 是枢纽里唯一的「人界面」：大盘、告警规则、屏蔽、值班、用户权限全在 Web UI； 对数据面它只做两件事——代理写（categraf → n9e :17000 → VM）与查询（PromQL → VM）。 部署形态＝单二进制、落板 A 的 systemd（riscv64 自建；官方发布物为 linux amd64/arm64）， 轻量模式内置 SQLite＋miniredis，解压即启、零外部 MySQL/Redis。 v6 起 n9e 不再生成 target_up 指标，机器失联以心跳超时判定（Targets 页在线态）， PromQL 层以 absent() 兜底。

为什么单二进制

官方 compose 五件套（VM＋n9e＋MySQL＋Redis＋categraf）对两板小场景是重步；轻量模式只净增 一个进程＋一个 n9e.db，运维重量与现栈同量级，且与板上既有 systemd 体系一致（自启、日志、回退 都用 systemctl）。升级路径＝etc 配置改外接 MySQL/Redis（多实例 HA 同路）， 部署形态不变。

代价（已接受）

miniredis 内存态：重启丢登录态（重登）与心跳态（分钟级重建）；SQLite 单文件： 灾备＝文件备份＋规则/大盘 JSON 导出入仓。官方将轻量模式定位为测试/体验，生产建议外接 MySQL/Redis——单用户场景接受，扩容路径清晰。AI 助手功能需真 Redis Streams（不用，不受影响）。 另需盯两件运行期事项：板 A 的存储/内存余量（R6）与 riscv64 上长跑稳定性（R7）。

07迁移路径（P0–P6）

每阶段独立可回退、有硬验证门；板端动作集中在 P3 一次完成（两板同一维护窗口）。 详细动作清单、验证门与回退手段见 spec §6。

  1. 前置与门禁（可先于新板到位） riscv64 自建三件 spike（categraf / VM / n9e，优先板上原生构建）· 板 A 存储内存余量实测 · 板 P → 板 A :17000 可达 · 板清单定稿 · 冻结物 md5 复核 · 物理映射定案
  2. 枢纽骨架（板 A） VM 落位（vmdata · 90d）＋ n9e 落位（内置 SQLite）＋ 两件 systemd enable · 建用户/业务组 · n9e 配 VM 为默认数据源＋写入代理 · LAN 窄放行 · 门禁：板 P→:17000 端到端、UI 可查 VM 样本、重启自启
  3. 存储并行（板零改动） VM 以 -promscrape.config 直抓两板三目标（复制 prometheus.yml 语义）· 与旧链路双跑 ≥7d · dashboard.html ?prom=<板 A>:8428 只读并行 · 门禁：指标对账＋CORS 实测
  4. Categraf 上板（唯一板端阶段 · 两板） 两板部署（钉核：板 P=0-7 / 板 A=8-15）→ node_* / hwmon / evald_* / 标签注入 / up 兼容流逐项对账 · 门禁：与 P2 数据一致、板 P A100 簇零监控进程、两车道漂移 ≤5% · 回退：stop categraf 即回 P2
  5. 告警上线（能力新增） 9 族规则录入 n9e（先仅记录 ≥3d）＋ 通知媒介 ＋ 计时天窗屏蔽 · 门禁：停 evald-acc 演练离线告警与恢复、历史回放验证阈值族、屏蔽窗口静默
  6. 大盘重建 四层大盘在 n9e 逐层落地（漏斗→堆叠柱）· 门禁：与 dashboard.html 并排对数一致后才谈退役
  7. 退役收尾（逐项独立回退） VM 直抓任务撤 · k1-prom 容器封存（卷留 30d）· 两板 node_exporter 停用（crontab 注释、文件保留）· dashboard.html 归档只读 · monitor-next/README 记录接替关系
